# Аудит ботов и модулей — предложения для обсуждения

Дата: 2026-10-06. Статус: **на обсуждении, ничего не изменено**.
Каждое предложение имеет номер (A1, B2 …). Решение по каждому — «делаем / не делаем / позже».
Каждое изменение логики проверяется эталонным тестом (`tester/README.md`) и сравнивается
с эталоном liq-grab: −200.40 USD, PF 0.84 (`tester/results/2026-10-06_liq-grab_reference.md`).

## 2. Критичные проблемы — риск для денег (делать первыми)

### A1. Все боты по умолчанию с одним `MagicNumber = 77777`
Если два бота работают на одном счёте и символе, они считают позиции друг друга своими:
`PositionGuardHasOpen` блокирует вход «чужой» позицией, `PositionGuardCloseAll` на границе
сессии **закрывает позиции другого бота**, безубыток двигает чужие стопы.
**Предложение:** уникальный magic по умолчанию для каждого бота (например, liq-grab 71001,
crt-bot 71002, engulfing 71003) + предупреждение в журнале при старте.
Логику торговли не меняет.

### A2. crt-bot считает лот от маржи, а не от стоп-лосса (`LOT_BY_MARGIN`)
Лот = 3% баланса / маржа за 1 лот. Риск сделки зависит от **плеча**, а не от расстояния
до SL. Пример: 200 USD, золото ~4150, 1 лот = 100 унций:
- плечо 1:2000 → маржа ≈ 207 USD за лот → лот 0.02 → при SL 1.5–3.2 USD риск 3–6 USD
  (1.5–3%) — случайно близко к задуманному;
- плечо 1:200 → маржа ≈ 2075 USD → расчётный лот 0.003 → минимальный 0.01 (см. A3);
- плечо выше 1:2000 (у Exness доступно и больше) → маржа ещё меньше → **лот растёт
  пропорционально плечу**, риск на сделку может уйти в десятки процентов депозита.

Смена плеча в личном кабинете молча меняет риск бота в разы.
**Предложение:** перевести crt-bot на расчёт от SL (`LOT_BY_TICK_VALUE`, как у остальных),
стратегию `LOT_BY_MARGIN` удалить из модуля.

### A3. Минимальный лот превышает заданный риск — бот всё равно торгует
`BrokerCalcLot` округляет вниз и поднимает до `SYMBOL_VOLUME_MIN`. При 200 USD
расчётный лот меньше 0.01, бот торгует 0.01, и фактический риск растёт по мере падения
баланса (в эталонном тесте: от 1.6% до >10% на сделку).
**Предложение:** новый параметр `MaxRiskOvershoot` (например, 1.5): если риск минимального
лота больше `RiskPercent × 1.5` — сделка пропускается с записью в журнал.
Это стандартная практика для малых счетов (см. источники [9], [10]).

### A4. Спред не учитывается по-настоящему
- liq-grab: `MaxSpread = 1000` пунктов = 1.00 USD на золоте — фильтр фактически выключен.
- engulfing: `MaxSpreadPips = 0` — выключен.
- crt-bot: фильтра спреда нет.

На счёте Exness Standard спред золота обычно 0.20–0.35 USD [7]. При стопе liq-grab 3.175 USD
это **6–11% от стопа на каждой сделке**, при ~36 сделках в день — главный «налог» стратегии.
**Предложение:** единый фильтр спреда в модуле исполнения, заданный **относительно стопа**
(например, спред ≤ 10% расстояния до SL), а не в абсолютных пунктах.

### A5. Тест на другом типе счёта, чем реальный
На демо-счёте символ `XAUUSD` без комиссии, на реальном — `XAUUSDm` (Standard).
Спреды могут отличаться, и эталон может быть оптимистичнее реала.
**Предложение (действие с твоей стороны):** открыть в приложении MT5 демо-счёт Exness
типа **Standard** (там будет `XAUUSDm`) и обновить секреты в GitHub. Эталонный тест
повторить на нём — это и будет окончательный эталон.

## 3. Архитектура: объединение и упрощение

### B1. Общий модуль входных параметров сессий
22 одинаковых `input` и ~80 одинаковых строк заполнения `SelectedSessionsConfig` +
`SessionConfig` в `OnInit` повторены в трёх ботах.
**Предложение:** `Include/Inputs/SessionInputs.mqh` (входные параметры) +
функция `SessionsSetup()` (заполнение и сводка в журнал). В ботах — одна строка вызова.
Логика не меняется, удаляется ~250 строк дублей.

### B2. Один фильтр сессий вместо двух
В `SessionFilter.mqh` два независимых механизма: «legacy» (окно вокруг стыка
Америка/Азия + закрытие перед закрытием Америки) и «Selected Sessions» (Asian/London/NY в UTC).
Они пересекаются по смыслу и усложняют `OnTick`.
**Предложение:** один фильтр с понятным API: «торговать ли сейчас», «закрывать ли
позиции сейчас», «не входить за N минут до конца сессии». Legacy-окно станет частным
случаем. Делать **после** A–C, отдельным шагом, с проверкой эталоном.

### B3. Один трейлинг вместо двух
crt-bot содержит собственную реализацию SyncTrail (~150 строк), а в общем диспетчере
режим SYNC — пустая заглушка. Кроме того, crt-bot использует `ENUM_TRAILING_MODE`,
а остальные — `ENUM_TRAILING_MODE_EX`.
**Предложение:** перенести реализацию SyncTrail из crt-bot в `Include/Trailing/SyncTrail.mqh`,
подключить в диспетчер, оставить один enum. Тогда SYNC появится во всех ботах.

### B4. Общий модуль «ожидание входа» (EntryManager)
crt-bot и engulfing содержат почти одинаковую машину состояний: сигнал → ожидание
уровня → режимы MARKET / SWEEP+RECLAIM / LIMIT → таймаут через N баров → отмена лимитки.
**Предложение:** `Include/EntryManager.mqh` с этой логикой. Бот только сообщает
«уровень, направление, SL, TP, срок». Исправления в одном месте сразу для обоих.

### B5. Единые единицы измерения
Параметры называются `...Pips`, а на деле это пункты; `adjustedPoint` зависит от
количества знаков (на золоте с 2 знаками пункт в 10 раз мельче, чем с 3).
Один и тот же набор параметров даёт разные стопы у разных брокеров.
**Предложение:** для золота задавать расстояния в **долларах цены** (`SL = 3.0` USD)
или в долях **ATR** (см. D4). Переименовать параметры честно.

### B6. Чистка мелочей
- `Comment()` и `Print` на каждом тике в некоторых ветках (спред у engulfing) —
  засоряют журнал; печатать только при изменении состояния.
- `ENUM_ENTRY_MODE` объявлен в двух ботах одинаково → в общий модуль (с B4).
- Шаблонный код `OnInit` (печать трейлинга, тренда) → функции модулей.

## 4. Исполнение и надёжность (TradeExecutor, BrokerAdapter)

### C1. Классификация ошибок и повтор отправки
Сейчас при любой ошибке `OrderSend` сделка просто теряется (в engulfing повтор
только на следующем тике, без разбора причины).
**Предложение:** временные ошибки (`REQUOTE`, `PRICE_CHANGED`, `PRICE_OFF`, `TIMEOUT`,
`CONNECTION`) — до 2 повторов с обновлённой ценой; постоянные (`NO_MONEY`,
`INVALID_STOPS`, `MARKET_CLOSED`, `TRADE_DISABLED`) — без повтора, с понятной записью
в журнал; после N ошибок подряд — пауза торговли на M минут [5].

### C2. Проверка перед отправкой
- `OrderCheck()` — маржа и корректность до отправки.
- `SYMBOL_TRADE_FREEZE_LEVEL` — сейчас учитывается только `STOPS_LEVEL`.
- Проверка, что рынок открыт (`SYMBOL_TRADE_MODE`, торговая сессия символа).
- Минимальная дистанция стопа — с учётом текущего спреда.

### C3. Проскальзывание
`SetDeviationInPoints(20)` = 0.02 USD на золоте — слишком мало для Market Execution
и бессмысленно для Instant. **Предложение:** параметр `MaxSlippage` в долях стопа;
после исполнения сравнивать фактическую цену с запрошенной и писать в журнал —
это даст реальную статистику проскальзывания на реальном счёте.

### C4. Журнал сделок для сравнения «тестер ↔ реал»
**Предложение:** при каждом входе/выходе писать строку в CSV (`MQL5/Files`): время сигнала,
запрошенная цена, фактическая цена, спред, проскальзывание, задержка исполнения в мс.
Тогда реальную торговлю можно сравнить с тестером сделка-в-сделку — это прямой
ответ на главный вопрос ТЗ.

## 5. Логика ботов

### 5.1. liq-grab (по ТЗ)

**Слабые стороны (что ломается при переходе в реал):**
1. **Вход внутри незакрытой свечи** (`rates[0].low/close`). Условие «пробил и вернулся»
   проверяется на каждом тике; в тестере и в реале тики разные → разные сделки.
   Это известная причина «красивого тестера» [2], [3].
2. **Стоп не привязан к структуре.** SL = фиксированные 3175 пунктов от цены входа,
   а не за экстремум снятой ликвидности. Логика «сняли лоу → возврат» теряет смысл,
   если стоп стоит не за этим лоу.
3. **Безубыток на 0.5R** закрывает 44% сделок около нуля (эталон: 469 из 1063),
   при этом до TP доходят только 27% сделок при нужных >33% для RR 1:2 [6].
4. **Слишком частые входы**: ~36 сделок в день на M3 только в Лондон → спред и
   проскальзывание съедают преимущество (см. A4).
5. **Тренд по «цепочке экстремумов»** с `static int current_trend`, который не
   сбрасывается: тренд, определённый часы назад, продолжает действовать.
6. **Размер позиции и спред** — см. A3, A4.

**Идея торговли — что имеет смысл изменить:**
- D1. Сигнал только по **закрытой** свече: свеча [1] пробила уровень и закрылась
  обратно за ним. Вход — на открытии следующей свечи.
- D2. **SL за экстремум снятия** + буфер (в долях ATR), а не фиксированный.
- D3. TP: фиксированный RR (2.0) как базовый вариант; как опция — ближайший
  противоположный уровень ликвидности, если он дальше 1.5R.
- D4. Минимальный и максимальный размер стопа — в долях ATR(14), чтобы стоп
  «дышал» вместе с волатильностью золота [8].
- D5. Безубыток: сравнить на эталоне 3 варианта — без безубытка / на 1R / на 0.5R
  (текущий). Оставить тот, что лучше на **всём** периоде, а не на одном месяце.
- D6. Лимит сделок за сессию (например, не больше 3) и пауза после 2 стопов подряд.
- D7. Сброс тренда, если за N баров не подтвердился.

### 5.2. crt-bot
- Сигналы по закрытым свечам — это правильно.
- Критично: A2 (лот от маржи).
- По умолчанию трейлинг выключен, тренд-фильтр включён — нужно проверить эталоном
  с теми же условиями, что liq-grab (отдельный `tester/crt-bot.json`).
- `CalcCRTLevels`: TP «не меньше 1R» — разумно; SL ограничен Min/Max в пунктах (см. B5).

### 5.3. engulfing-bot
- Сигнал по закрытым свечам — правильно; вход на 50% тела — разумная идея.
- Фильтр спреда выключен по умолчанию (A4); при включённом — печать на каждом тике (B6).
- Параметры с `Pips` в названии — пункты (B5).

### 5.4. crt-push
- Только уведомления. Логика корректная: закрытые свечи, антидубль через
  GlobalVariable. Изменений не требует, кроме общих B-пунктов (если затронут CrtDetector).

## 6. Тестирование и оптимизация

- E1. **Эталон для каждого бота**: `tester/crt-bot.json`, `tester/engulfing.json`
  с теми же эталонными условиями. Сейчас эталон есть только у liq-grab.
- E2. **Разделение периода**: подбор параметров на 2026.07.06–2026.09.05,
  проверка на 2026.09.05–2026.10.05 (данные, которых бот «не видел»).
  Если на проверочном месяце результат хуже чем вдвое — параметры переподогнаны [4].
- E3. **Мало параметров**. Оптимизировать не больше 2–3 параметров за раз,
  остальные фиксировать. Каждый лишний параметр увеличивает риск подгонки.
- E4. **`OnTester()`**: собственная метрика (например, PF × √сделок, с отсечкой при
  просадке > 30%), чтобы оптимизатор не выбирал «случайно удачные» наборы.
- E5. Учесть ограничение тестера: `TimeGMT()` в тестере равен времени сервера [11].
  У Exness сервер GMT+0, поэтому сейчас ошибки нет, но при смене брокера сессии
  в тестере сдвинутся. **Предложение:** в тестере брать смещение только из параметра.

## 7. Чего делать не стоит

- **Мартингейл, сетки, усреднение** — улучшают тестер, в реале ведут к сливу.
- **Подбор 10+ параметров на 3 месяцах** — гарантированная подгонка под историю.
- **Сужение стопа ради «красивого» RR** — на золоте со спредом 0.2–0.35 USD узкий стоп
  выбивается шумом и спредом.
- **Добавление индикаторных фильтров «на всякий случай»** (RSI + MACD + …) — каждый
  режет количество сделок и добавляет параметр для подгонки; добавлять только то,
  что улучшает результат на проверочном периоде.
- **Трейлинг по каждому тику на M3** — превращает прибыльные сделки в безубыточные
  на шуме (видно по эталону).
- **Скачанные «готовые» фильтры без проверки эталоном** — только через тест.
